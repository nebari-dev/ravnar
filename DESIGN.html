Design: Dynamic Agent Registration

Summary

Add runtime CRUD endpoints to register and unregister agents without restarting the server. Agent configuration is split into static (loaded from YAML at startup, unchanged from today) and dynamic (registered at runtime via API, ephemeral — lost on restart). The CRUD endpoints are gated behind a feature flag in the YAML config. The existing GET /api/config response is slimmed down, and a new GET /api/agents endpoint provides the merged view of all available agents.

Goals

  • Allow runtime registration of new agents via API without a server restart.
  • Support registering any agent type that can be expressed as an ImportStringWithParams blob (the same mechanism used by static config).
  • Provide a feature flag to disable dynamic agent registration entirely.
  • Keep static agents fully intact — they cannot be deleted via the API.
  • Ensure the server always has at least one usable agent (static or dynamic-enabled).
  • Preserve backward compatibility for the static config shape as much as possible (alpha — breaking changes acceptable).

Non-Goals

  • Persistent storage for dynamic agents — they are in-memory only (ephemeral).
  • Agent update endpoint — delete + recreate is the pattern.
  • Authorization / access control for the CRUD endpoints (will be added later as an admin feature).
  • Handling threads that reference a now-deleted agent (deferred to a future design).
  • UI changes — API-only; the frontend will be updated separately.

Background / Motivation

Ravnar currently loads all agents from YAML configuration at startup. Adding or removing agents requires editing the config file and restarting the server. For multi-tenant or dynamic environments, this is too inflexible. Operators need the ability to register new agents (e.g., SSE backends, new AI models) at runtime through an API.

The existing agent config mechanism uses ImportStringWithParams — a Pydantic model that accepts a Python import path (cls_or_fn) and a params dict. This model is fully JSON-serializable and is already the standard way to configure agents. Dynamic registration reuses this same mechanism, so any agent type that can be defined in YAML can also be registered via API.

Design

1. Config Model Changes

The current BaseConfig.agents field is a flat dict: 

agents: dict[str, ImportStringWithParams[Agent]]

This is restructured into a nested config:

class DynamicAgentConfig(BaseModel, RenderableMixin):
    enabled: bool = False


class AgentConfig(BaseModel, RenderableMixin):
    static: dict[str, ImportStringWithParams[Agent]] = Field(
        default_factory=lambda: {
            "default": ImportStringWithParams(cls_or_fn=DefaultAgent),
        }
    )
    dynamic: DynamicAgentConfig = Field(default_factory=DynamicAgentConfig)

    @model_validator(mode="after")
    def _ensure_not_agentless(self) -> Self:
        if not self.static and not self.dynamic.enabled:
            raise ValueError(
                "At least one static agent must be configured, or dynamic agents must be enabled."
            )
        return self

The default_factory preserves today's default: a single default agent using DefaultAgent.

The model validator prevents a dead-end configuration where there are no static agents and dynamic agents are disabled — which would leave the server with zero usable agents.

The corresponding YAML config changes from:

agents:
  gpt:
    cls_or_fn: ravnar.agents.PydanticAiAgentWrapper
    params: { ... }

To:

agents:
  static:
    gpt:
      cls_or_fn: ravnar.agents.PydanticAiAgentWrapper
      params: { ... }
  dynamic:
    enabled: false

The existing BaseConfig field type changes from dict[str, ImportStringWithParams[Agent]] to AgentConfig. Env var override becomes RAVNAR_AGENTS__DYNAMIC__ENABLED=true.

2. API Response Models

class APIConfig(BaseModel):
    dynamic_agents_enabled: bool


class AgentInfo(BaseModel):
    id: str
    capabilities: ag_ui.core.AgentCapabilities
    quick_prompts: list[QuickPrompt]

Note: AgentInfo replaces the old AgentConfig schema name (which now refers to the config model above). Rename to avoid ambiguity: schema.api.AgentConfig → schema.api.AgentInfo.

3. API Endpoints

MethodPathAuthDescription
GET /api/config Yes Returns {dynamicAgentsEnabled: bool}. Agent list removed from this endpoint — moved to /api/agents.
GET /api/agents Yes Returns merged list of all agents (static + enabled dynamic). Response: list[AgentInfo].
POST /api/agents Yes Register a new dynamic agent. Gated — returns 403 Forbidden if agents.dynamic.enabled is false. Body: {id: str, agent: ImportStringWithParams}. Rejects duplicate IDs (including static agent IDs) with 409 Conflict.
DELETE /api/agents/{id} Yes Unregister a dynamic agent. Gated — returns 403 Forbidden if agents.dynamic.enabled is false. Returns 403 Forbidden if the ID belongs to a static agent (static agents are protected). Returns 404 Not Found if the dynamic agent ID does not exist.
POST /api/agents/{id}/run Yes Unchanged — runs any agent (static or dynamic) by ID. Always available.

4. AgentHandler Changes

The AgentHandler class is extended with two agent pools:

class AgentHandler:
    def __init__(self, agent_config: AgentConfig) -> None:
        # Static agents — loaded from config, never modified
        self._static_agents: dict[str, Agent] = {
            id: factory()
            for id, factory in agent_config.static.items()
        }
        # Dynamic agents — registered at runtime, ephemeral
        self._dynamic_agents: dict[str, Agent] = {}
        self._dynamic_agent_factories: dict[str, Callable[[], Agent]] = {}
        self._event_encoder = ag_ui.encoder.EventEncoder()
        self._dynamic_enabled = agent_config.dynamic.enabled

    @property
    def configs(self) -> list[schema.AgentInfo]:
        # No longer cached — the set can change at runtime
        agents = dict(self._static_agents)
        if self._dynamic_enabled:
            agents.update(self._dynamic_agents)
        return [
            schema.AgentInfo(id=id, capabilities=agent.get_capabilities(),
                             quick_prompts=agent.get_quick_prompts())
            for id, agent in agents.items()
        ]

    def assert_available(self, agent_id: str) -> None:
        if agent_id not in self._static_agents and agent_id not in self._dynamic_agents:
            raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Agent not found")

    def add_agent(self, agent_id: str, factory: Callable[[], Agent]) -> None:
        if agent_id in self._static_agents or agent_id in self._dynamic_agents:
            raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail="Agent ID already exists")
        self._dynamic_agents[agent_id] = factory()
        self._dynamic_agent_factories[agent_id] = factory

    def remove_agent(self, agent_id: str) -> None:
        if agent_id in self._static_agents:
            raise HTTPException(status_code=status.HTTP_403_FORBIDDEN,
                                detail="Static agents cannot be deleted")
        if agent_id not in self._dynamic_agents:
            raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Agent not found")
        del self._dynamic_agents[agent_id]
        del self._dynamic_agent_factories[agent_id]

The factory is retained (_dynamic_agent_factories) to support potential future persistence; currently dynamic agents are ephemeral and lost on restart.

5. Gating the CRUD Endpoints

The agents.py router receives the AgentHandler and inspects handler.dynamic_enabled. The POST and DELETE endpoints return 403 Forbidden immediately if dynamic agents are disabled. The GET /api/agents endpoint is always available (it returns whatever agents exist). 

@router.post("")
async def register_agent(
    *,
    handler: AgentHandler = Depends(get_agent_handler),
    data: schema.RegisterAgentData,
) -> schema.AgentInfo:
    if not handler.dynamic_enabled:
        raise HTTPException(status_code=status.HTTP_403_FORBIDDEN,
                            detail="Dynamic agent registration is disabled")
    agent = data.agent()
    handler.add_agent(data.id, lambda: data.agent())
    return schema.AgentInfo(
        id=data.id,
        capabilities=agent.get_capabilities(),
        quick_prompts=agent.get_quick_prompts(),
    )

6.

The schema.api.AgentConfig model is renamed to AgentInfo to free the name for the new config model in config.py. The old APIConfig.agents field is removed; the new APIConfig only carries dynamic_agents_enabled.

Tradeoffs & Risks

Ephemeral dynamic agents

Dynamic agents are in-memory only. A server restart loses all registered agents. This is intentional for now — the user explicitly requested ephemeral storage. If persistence is needed later, the dynamic agent configs can be stored in the database using _dynamic_agent_factories (already retained).

No authorization on CRUD endpoints

Anyone with API access can register arbitrary agents, including those that import and execute arbitrary Python code (via ImportStringWithParams). This is a known security gap. It is explicitly deferred because ravnar's authenticator system is currently rudimentary and not ready for role-based access. Authorization will be added later as an admin-only gate.

Status code for static agent deletion

The design uses 403 Forbidden when attempting to delete a static agent. Alternatives considered:

  • 409 Conflict — the resource's state (static) conflicts with the operation. Also defensible.
  • 400 Bad Request — too generic.
  • 405 Method Not Allowed — misleading because DELETE is a valid method on the endpoint.

403 was chosen because it most precisely conveys the server policy: "you are forbidden from deleting static agents, full stop." This can be revisited if a different code fits the wider API conventions better.

Breaking config change

The YAML config format changes from agents: {id: {...}} to agents: {static: {id: {...}}, dynamic: {enabled: ...}}. This is acceptable given alpha status, but the error message when a user provides the old format should be clear. Pydantic's validation error on the new model will naturally catch this, but it might be worth adding a pre-check validator that detects the old flat structure and warns with a migration hint.

Merging the two agent pools

The GET /api/agents response does not distinguish static from dynamic agents. This is intentional — the caller just needs the list of available agents. If differentiation is needed later, a source: "static" | "dynamic" field can be added to AgentInfo.

Threads referencing deleted agents (deferred)

When a dynamic agent is deleted, existing threads that reference it become problematic. Running a new run on that thread will fail with 404 because assert_available will reject the agent ID. This is unresolved and deferred to a future design. Options for that future design include: soft-delete/archive agents, reassign threads to a fallback agent, or allow stale agent IDs on threads (failing at run time with a user-friendly error).

Open Questions

  • Threads and deleted agents: What should happen when a user tries to view or run a thread whose agent has been deleted? Deferred to a future design session.
  • Status code for static agent deletion: Currently 403 Forbidden. Acceptable, or prefer 409 Conflict?
  • Agent factory re-instantiation: add_agent currently calls the factory immediately and also stores the factory. If the factory is expensive (e.g., connects to external services on init), should instantiation be lazy? For now, eager instantiation matches how static agents work.
