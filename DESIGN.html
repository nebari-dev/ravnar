Design: Dynamic Agent Registration

Summary

Add runtime CRUD endpoints to register and unregister agents without restarting the server. Agent configuration is split into static (loaded from YAML at startup, unchanged from today) and dynamic (registered at runtime via API, ephemeral — lost on restart). The CRUD endpoints are only mounted when the feature flag in the YAML config is enabled. The existing GET /api/config response is slimmed down, and a new GET /api/agents endpoint provides the merged view of all available agents.

Goals

  • Allow runtime registration of new agents via API without a server restart.
  • Support registering any agent type that can be expressed as an ImportStringWithParams blob (the same mechanism used by static config).
  • Provide a feature flag to disable dynamic agent registration entirely — when disabled, the POST/DELETE routes are not mounted.
  • Keep static agents fully intact — they cannot be deleted via the API.
  • Ensure the server always has at least one usable agent (static or dynamic-enabled).
  • Preserve backward compatibility for the static config shape as much as possible (alpha — breaking changes acceptable).

Non-Goals

  • Persistent storage for dynamic agents — they are in-memory only (ephemeral).
  • Agent update endpoint — delete + recreate is the pattern.
  • Authorization / access control for the CRUD endpoints (will be added later as an admin feature).
  • Handling threads that reference a now-deleted agent (deferred to a future design).
  • UI changes — API-only; the frontend will be updated separately.

Background / Motivation

Ravnar currently loads all agents from YAML configuration at startup. Adding or removing agents requires editing the config file and restarting the server. For multi-tenant or dynamic environments, this is too inflexible. Operators need the ability to register new agents (e.g., SSE backends, new AI models) at runtime through an API.

The existing agent config mechanism uses ImportStringWithParams — a Pydantic model that accepts a Python import path (cls_or_fn) and a params dict. This model is fully JSON-serializable and is already the standard way to configure agents. Dynamic registration reuses this same mechanism, so any agent type that can be defined in YAML can also be registered via API.

Design

1. Config Model Changes

The current BaseConfig.agents field is a flat dict: 

agents: dict[str, ImportStringWithParams[Agent]]

This is restructured into a nested config:

class DynamicAgentConfig(BaseModel, RenderableMixin):
    enabled: bool = False


class AgentConfig(BaseModel, RenderableMixin):
    static: dict[str, ImportStringWithParams[Agent]] = Field(
        default_factory=lambda: {
            "default": ImportStringWithParams(cls_or_fn=DefaultAgent),
        }
    )
    dynamic: DynamicAgentConfig = Field(default_factory=DynamicAgentConfig)

    @model_validator(mode="after")
    def _ensure_not_agentless(self) -> Self:
        if not self.static and not self.dynamic.enabled:
            raise ValueError(
                "At least one static agent must be configured, or dynamic agents must be enabled."
            )
        return self

The default_factory preserves today's default: a single default agent using DefaultAgent. This ensures existing configs that don't specify agents at all still get a default agent.

The model validator prevents a dead-end configuration where there are no static agents and dynamic agents are disabled — which would leave the server with zero usable agents.

The corresponding YAML config changes from:

agents:
  gpt:
    cls_or_fn: ravnar.agents.PydanticAiAgentWrapper
    params: { ... }

To:

agents:
  static:
    gpt:
      cls_or_fn: ravnar.agents.PydanticAiAgentWrapper
      params: { ... }
  dynamic:
    enabled: false

The existing BaseConfig field type changes from dict[str, ImportStringWithParams[Agent]] to AgentConfig. Env var override becomes RAVNAR_AGENTS__DYNAMIC__ENABLED=true.

2. API Response Models

class APIConfig(BaseModel):
    dynamic_agents_enabled: bool


class AgentInfo(BaseModel):
    id: str
    capabilities: ag_ui.core.AgentCapabilities
    quick_prompts: list[QuickPrompt]

Note: AgentInfo replaces the old AgentConfig schema name (which now refers to the config model in config.py).

3. API Endpoints

MethodPathAuthDescription
GET /api/config Yes Returns {dynamicAgentsEnabled: bool}. Agent list moved to /api/agents.
GET /api/agents Yes Returns merged list of all agents (static + enabled dynamic). Response: list[AgentInfo]. Always mounted.
POST /api/agents Yes Register a new dynamic agent. Only mounted when agents.dynamic.enabled is true. Body: {id: str, agent: ImportStringWithParams}. Returns 200 OK with the created AgentInfo (matches ravnar convention — other POST endpoints return 200). Rejects duplicate IDs (including static agent IDs) with 409 Conflict.
DELETE /api/agents/{id} Yes Unregister a dynamic agent. Only mounted when agents.dynamic.enabled is true. Returns 403 Forbidden if the ID belongs to a static agent (static agents are protected — distinct from "endpoint not mounted" 404). Returns 404 Not Found if the dynamic agent ID does not exist.
POST /api/agents/{id}/run Yes Unchanged — runs any agent (static or dynamic) by ID. Always available.

Gating strategy

When agents.dynamic.enabled is false, the router factory (make_agents_router) simply omits the POST / and DELETE /{id} routes. The GET /api/agents and POST /api/agents/{id}/run routes are always present. This means a disabled server returns 404 Not Found for POST /api/agents and DELETE /api/agents/{id} — the routes simply don't exist.

Why not return 403 instead? When authorization is added later, 403 will mean "the endpoint exists but you (the authenticated user) are not permitted." Using 404 for "feature not available" keeps these two cases clearly distinct. An unauthenticated user and a disabled feature both look like the endpoint doesn't exist — which is fine because a client that doesn't know about dynamic agents shouldn't be trying these endpoints anyway.

Static agent deletion

The DELETE /api/agents/{id} endpoint returns 403 Forbidden when the ID belongs to a static agent. This is a different kind of denial: the resource exists but the server's policy forbids modifying it. A disabled-feature 404 would be misleading here — the endpoint is mounted and the agent exists, so "not found" is wrong. 403 precisely conveys "this operation is not permitted on this resource."

4. AgentHandler Changes

The AgentHandler class is extended with two agent pools:

class AgentHandler:
    def __init__(self, agent_config: AgentConfig) -> None:
        # Static agents — loaded from config, never modified
        self._static_agents: dict[str, Agent] = {
            id: factory()
            for id, factory in agent_config.static.items()
        }
        # Dynamic agents — registered at runtime, ephemeral
        self._dynamic_agents: dict[str, Agent] = {}
        self._event_encoder = ag_ui.encoder.EventEncoder()
        self._dynamic_enabled = agent_config.dynamic.enabled

    def infos(self) -> list[schema.AgentInfo]:
        """Return info for all available agents (static + dynamic)."""
        agents = dict(self._static_agents)
        if self._dynamic_enabled:
            agents.update(self._dynamic_agents)
        return [
            schema.AgentInfo(
                id=id,
                capabilities=agent.get_capabilities(),
                quick_prompts=agent.get_quick_prompts(),
            )
            for id, agent in agents.items()
        ]

    @property
    def dynamic_enabled(self) -> bool:
        return self._dynamic_enabled

    def assert_available(self, agent_id: str) -> None:
        if agent_id not in self._static_agents and agent_id not in self._dynamic_agents:
            raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Agent not found")

    def add_agent(self, agent_id: str, agent: Agent) -> None:
        if agent_id in self._static_agents or agent_id in self._dynamic_agents:
            raise HTTPException(status_code=status.HTTP_409_CONFLICT, detail="Agent ID already exists")
        self._dynamic_agents[agent_id] = agent

    def remove_agent(self, agent_id: str) -> None:
        if agent_id in self._static_agents:
            raise HTTPException(status_code=status.HTTP_403_FORBIDDEN,
                                detail="Static agents cannot be deleted")
        if agent_id not in self._dynamic_agents:
            raise HTTPException(status_code=status.HTTP_404_NOT_FOUND, detail="Agent not found")
        del self._dynamic_agents[agent_id]

Key changes from today:

  • configs (cached property) → infos() (regular method). No caching because the set changes at runtime.
  • add_agent takes an already-instantiated Agent — the caller (the API handler) is responsible for calling the factory.
  • No factory storage — agents are eagerly instantiated and ephemeral.
  • The GET /api/config handler no longer calls handler.configs. It just returns {"dynamicAgentsEnabled": handler.dynamic_enabled}.

5. Router wiring

The agents router factory now takes the AgentHandler and conditionally registers the POST/DELETE endpoints: 

def make_router(*, agent_handler: AgentHandler, authenticated_user: ...) -> schema.APIRouter:
    router = schema.APIRouter(tags=["Agents"], dependencies=[Depends(authenticated_user)])

    @router.sse("/{agentId}/run", methods=["POST"], response_model=schema.Event, tags=["Runs"])
    async def create_stateless_run(...):
        return await agent_handler.run(agent_id, run_agent_input)

    if agent_handler.dynamic_enabled:
        @router.post("")
        async def register_agent(
            data: schema.RegisterAgentData,
        ) -> schema.AgentInfo:
            agent = data.agent()
            agent_handler.add_agent(data.id, agent)
            return schema.AgentInfo(
                id=data.id,
                capabilities=agent.get_capabilities(),
                quick_prompts=agent.get_quick_prompts(),
            )

        @router.delete("/{agentId}")
        async def unregister_agent(
            agent_id: Annotated[str, Path(alias="agentId")],
        ) -> None:
            agent_handler.remove_agent(agent_id)

    return router

The top-level GET /api/config in api/__init__.py is updated: 

    @router.get("/config")
    async def get_config() -> schema.APIConfig:
        return schema.APIConfig(dynamic_agents_enabled=agent_handler.dynamic_enabled)

6. Schema renames

The schema model formerly known as AgentConfig (in schema/api.py) is renamed to AgentInfo to avoid collision with the new config model in config.py. The old APIConfig.agents field is removed entirely; the new APIConfig only carries dynamic_agents_enabled.

A new RegisterAgentData model is added to schema/api.py: 

class RegisterAgentData(BaseModel):
    id: str
    agent: ImportStringWithParams[Agent]

Note: ImportStringWithParams is defined in config.py, not schema/. The schema module will need to import it, or it should be moved to a shared location. Since ImportStringWithParams is already imported extensively in config.py, the simplest approach is to export it from schema/__init__.py or import it directly from config. Using it in a request body model means FastAPI's OpenAPI generation will produce a schema for it — this is desirable because it documents the expected JSON shape.

Tradeoffs & Risks

Ephemeral dynamic agents

Dynamic agents are in-memory only. A server restart loses all registered agents. This is intentional for now — the user explicitly requested ephemeral storage. If persistence is needed later, the ImportStringWithParams dict from the request body can be stored in the database and re-instantiated on startup.

No authorization on CRUD endpoints

Anyone with API access can register arbitrary agents, including those that import and execute arbitrary Python code (via ImportStringWithParams). This is a known security gap. It is explicitly deferred because ravnar's authenticator system is currently rudimentary and not ready for role-based access. Authorization will be added later as an admin-only gate. At that point, POST /api/agents and DELETE /api/agents/{id} (which are mounted regardless of the gating flag at that point) will return 403 Forbidden for unauthorized users — which is distinct from today's behavior where the routes are unmounted and return 404.

Endpoint not mounted vs. endpoint returns 403

When the feature is disabled, the POST/DELETE routes are not mounted. The client gets a 404. When authz is added later and the feature is enabled, an unauthorized user will get a 403. These are intentionally different:

  • 404 = "this capability is not available on this server"
  • 403 = "this capability exists but you can't use it"

Breaking config change

The YAML config format changes from agents: {id: {...}} to agents: {static: {id: {...}}, dynamic: {enabled: ...}}. This is acceptable given alpha status, but the error message when a user provides the old format should be clear. Pydantic's validation error on the new model will naturally catch this, but a pre-check validator that detects the old flat structure and warns with a migration hint would improve the developer experience.

No source attribution in GET /api/agents

The GET /api/agents response does not distinguish static from dynamic agents. This is intentional — the caller just needs the list of available agents. If differentiation is needed later, a source: "static" | "dynamic" field can be added to AgentInfo.

Threads referencing deleted agents (deferred)

When a dynamic agent is deleted, existing threads that reference it become problematic. Running a new run on that thread will fail with 404 because assert_available will reject the agent ID. This is unresolved and deferred to a future design. Options for that future design include: soft-delete/archive agents, reassign threads to a fallback agent, or allow stale agent IDs on threads (failing at run time with a user-friendly error).
